# spp-bots: bots that live like players

Status: **first version running** (see [Progress](#progress)); bots travel anywhere with
teleports, their houses and every kind of bank, woodcutters and miners travel to their spots,
and bots fight like players (eating, prayers, potions, specials, the right style; combat tasks
with looting rules); real players can hand their character to the bot with `::botmode`
(see [Travel](#travel-state-at-the-end-of-2026-11-09), [Combat](#combat-requested-2026-11-09) and
[Bot mode](#bot-mode-for-real-players)). This is the fork's plan for
reworking the bots. Upstream's bots are
mostly site crowds (skillers at a spot, PvP pens in the Wilderness, minigame fill). We want bots
that look and behave like ordinary OSRS players: a brain that picks what to do next, an account
with a believable history, and nothing visible from the outside that marks them as a bot.

## Decisions

| Question | Decision |
| --- | --- |
| Where | Our own plugin **spp-bots**: `server/plugins/spp-bots/`, registered as `SppBots`. See [Naming](#naming) |
| Upstream's bots (`plugins/bots/`) | **Disabled entirely** on our worlds. We reuse modules from it, but its plugin doesn't run |
| Minigame bots | **Remade from our plugin.** Upstream's minigame bot fill is turned off |
| Accounts | **Generated by simulation:** each bot's account is what a real player would have after playing that long. A mix of new, early, mid, late and endgame accounts |
| How many bots | **As many as the server can run without lag for real players.** Enforced by a live tick budget, not a fixed number |
| Client | RuneLite through `runelite-gateway` only; the web client isn't needed |
| Ironmen | **Normal ironmen** are in scope (no group, ultimate or hardcore) |
| Bot count | Decided after the bots run, by measuring |

## Ground rules

1. **Stay mergeable with upstream.** `plugins/bots/` gets 200+ upstream commits a quarter.
   Every line we change there is a future conflict.
   - New behaviour goes in **our plugin**.
   - We change upstream files only through **generic, small changes we would send upstream
     anyway**: a config flag, a hook, a correctness fix. Each one is listed under
     [Upstream-able changes](#upstream-able-changes) so we know what to PR.
   - Per-world settings go in `data/definitions/world.local.json` (gitignored), never in
     `world.json` or `bot-sites.json`.
2. **Bots keep `BotPlayerSession`.** No network packets, actions called directly. But a bot may
   only do what a player could do at that spot with those items and levels: no spawned gear,
   no teleporting without a teleport, no skipping requirements.
3. **Jagex is the reference.** Anything a real player sees on a bot (right-click menu, level
   shown, appearance, chat, movement, gear for its levels) must match what live OSRS shows for a
   player. Sources are the wiki and RSProx recordings of live OSRS, as in
   [server/AGENTS.md](../AGENTS.md).
4. **Real players come first.** Bots never make the tick slower for real players. See
   [Population and budget](#phase-3-population-and-tick-budget).
5. **The RuneLite gateway is the client we judge by.** New player-facing features must work
   through `runelite-gateway`: cache interfaces, chatbox prompts or chat, never a group-30000+
   interface or a plugin message. See [Phase 0c](#0c-gateway-only).

## Naming

The plugin is **spp-bots**:

| What | Value |
| --- | --- |
| Directory | `server/plugins/spp-bots/` |
| Registered name | `SppBots` (entry file `SppBots.plugin.js`) |
| Unit file suffix (rule 12) | `.SppBots.js`, e.g. `Brain.SppBots.js` |
| Config namespace | `pluginConfig` `"SppBots:*"`, e.g. `"SppBots:population"` |
| Custom events | `spp-bots:*` |
| Attribute keys (rule 14) | `spp-bots:*` |

`PluginManager` compares plugin names case-insensitively with punctuation removed
(`normalizePluginName`). `SppBots` becomes `sppbots`, which doesn't clash with upstream's
`PlayerBots` (`playerbots`), so the two can be switched separately.

Upstream's plugin is turned off with `"plugins": { "PlayerBots": false }` in
`world.local.json` (or `DISABLE_PLAYER_BOTS=1`, which filters by its path).

### 0a. Right-click shows combat level, not skill level

**Symptom:** right-clicking a player (bot or not) in RuneLite shows `(skill-N)` instead of
`(level-N)`.

**Cause:** the appearance block has two level fields, combat level and skill level. The client
shows `(skill-N)` whenever skill level isn't 0. Core fills it with the **total level** for
every player:

- [PlayerSession.ts:612-613](../src/main/typescript/elvarg/net/PlayerSession.ts#L612-L613) passes
  `getCombatLevel()` and `getTotalLevel()` to `encodePlayerAppearance`
- [ClientProtocol.ts:2970-2971](../src/main/typescript/elvarg/net/protocol/ClientProtocol.ts#L2970-L2971)
  writes them
- the gateway passes it straight through:
  [EntityMirror.kt:229](../../runelite-gateway/src/main/kotlin/gateway/session/EntityMirror.kt#L229)

**Fix:** send 0 for skill level by default, so everyone shows `(level-N)` as in live OSRS. If
some area really does show the skill total in OSRS, it becomes a generic per-player override
that an `Area` sets, not a default. Check the browser client too: if it reads the field
differently, it gets the same change.

- Upstream-able: **yes** (core correctness fix, affects all players).
- Verify: RuneLite through the gateway. Right-click a bot and a real player; both show
  `(level-N)`.

## Phase 1: bot identity

**State (2026-11-09):**

- [x] **1** persistent accounts: saves, stable names in the roster, a locked password (`lockedPassword`)
- [x] **2** indistinguishable (2026-11-09): run energy, hitpoints decay, NPC aggression (with a
  bot that decides whether to fight), and the `onPlayerProcess` opt-in are done; trading moves to
  Phase 6 with the rest of trade. Details below.
- [x] **3** names (`realisticName`), randomised looks, gear from levels and wealth (melee only so far)
- [x] **4** login schedule (2026-11-09). Sessions of 30-150 minutes (`sessionMinutes`). The
  online count follows the day (`Schedule.SppBots.js`): `online` is the peak at `peakHour` (20:00
  server time), falling on a cosine to `quietShare` (0.5) of it twelve hours later. Each bot has a
  favourite hour (`playHour` in the roster: 55% evening, 25% afternoon, 12% morning, 8% night)
  and is up to 4x likelier to log in near it. A session that's over ends at a bank: the bot banks
  everything and logs out there (5 minutes at most). When the target falls, one bot a tick ends
  its session that way; only above 1.25x the target do bots log out at once. Fixed on the way: a
  logout that hadn't landed still counted as online, so going over the target logged out every
  bot in one pass (195 to 26 for a target of 150). Checked: lowering the target from ~150 to 130,
  27 sessions ended and 26 of those bots banked first; the count settled at the target.

Before the brain, a bot has to *be* a player.

1. **Persistent accounts.** Every bot has a save, a stable name, and progress that carries
   across restarts. No `ATTR_SKIP_PERSISTENCE` for our bots. Bot accounts can't be logged in by
   anyone (random unusable password, as AI bots do).
2. **Indistinguishable from the outside.** Go through the 18 core `isPlayerBot()` carve-outs.
   For each, ask: can a real player observe the difference? If yes, it must go, or move behind
   something invisible.
   - Persistence and network skips are fine; nobody can see them.
   - Combat, death, shop, trade and movement differences are not.
   - Changes to core carve-outs are risky for the merge. Prefer a narrow flag upstream can
     accept (e.g. a player marked "behaves as a player") over deleting their checks.
3. **Appearance and names.** Realistic names (reuse `plugins/bots/ai/Names.PlayerBots.js`), a
   varied look set at creation, gear that fits the account's levels and wealth.
4. **Login schedule.** Each bot has play sessions with a start, a length and breaks, spread
   over the day, so the online count rises and falls like a real world. Logging in or out
   happens at a bank or a safe spot, like a person.

### Phase 1 step 2: the plan (2026-11-09)

Core has about 50 `isPlayerBot()` / `isUnwatchedBot()` checks. Most are invisible (client
packets, sounds and update loops for a bot with no client, log lines, messages only the bot
would get, PvP-world teleport rules). These five change what a player can see:

| Carve-out | Where | What a player notices |
| --- | --- | --- |
| NPC aggression skipped | `Player.process` (`NpcAggression.process`) | monsters ignore bots |
| `onPlayerProcess` not emitted | `World.ts`, process_players | timers, area rules and random events never apply to bots |
| Infinite run energy | `MovementQueue.drainRunEnergy` | bots run forever and never walk |
| Boosted hitpoints never decay | `Player` stat restore | an over-healed bot stays over its max |
| Run energy never recovers (it never drains either) | `Player.process` recovery | goes with infinite run energy |
| Trade special cases | `Trading.ts` | Phase 6: bots don't trade yet |

**Mechanism (upstream-able):** one flag, `Player.playsAsPlayer()` (default false). Each of
those checks becomes "a bot that doesn't play as a player"; upstream's bots are unchanged and
spp-bots switch it on at login.

**Order:**

1. [x] **Run energy and hitpoints decay** (2026-11-09). `Player.playsAsPlayer()` /
   `setPlaysAsPlayer()`, and `takesBotShortcuts()` for the visible shortcuts; spp-bots set it at
   login. Their energy drains and recovers as a player's (recovery counts the ticks an unwatched
   bot skipped); with none left they walk, and turn run back on at a level they pick between
   25 and 70% (players have `RunAutoEnable`, on `onPlayerProcess`). Boosted hitpoints drop back.
   Checked: a travelling bot went 92 → 68% running and 90 → 94% standing.
2. [x] **NPC aggression** (2026-11-09). Aggressive monsters attack bots that play as players
   (`Player.process`); a bot nobody watches gets the NPCs around it from the update buckets
   (`NpcAggression`). `Defence.SppBots.js`, every tick before the brain: when attacked the bot
   decides whether it **wants** the fight (a fighter, not a skiller, against a monster no higher
   level than itself). If not, it walks 18 tiles away with auto retaliate off until clear, and its
   activity picks somewhere else. If so, auto retaliate fights and the activity waits; it eats
   below 40-60% hitpoints (its own threshold per fight) and runs below 25-40% with nothing to
   eat. After a death (`onPlayerDeath`) it puts its kept gear back on and starts a new activity.
   Checked: a Mugger attacked a combat-3 main, which walked off; a level-20 dark wizard attacked
   two combat-25 mains, which fought and ran at 31-33% (one died and respawned in Lumbridge,
   kept items in its pack, before the re-equip was added; that part is unit-tested). Attacks are
   rare in normal play (one in 8 minutes with 200 bots): aggressive monsters ignore players over
   twice their level. Below, what this needed:
   - bots have no NPC list: aggression reads `getLocalNpcs()`, which the update loop fills only
     for players with a client (unwatched bots are skipped to save O(players²) work), so bots
     need their own nearby-NPC lookup for it
   - bots must answer an attack: fight back, eat, or run (spp-bots' brain has no `supportTick`
     yet), or a woodcutter beside aggressive monsters dies over and over
   - death recovery: `PlayerDeath` already takes the player path (items drop); afterwards the
     bot gets its tool back from the bank and picks an activity it can still do
3. [x] **`onPlayerProcess` by listener** (2026-11-09, mechanism). `api.onPlayerProcess(handler,
   { bots: true })`: such a listener also runs for bots that play as players
   (`PluginManager.emitBotPlayerProcess`, from the world's process loop); every other listener is
   unchanged, and none opts in yet, because nothing bots do so far needs one (gathering, banking,
   travel). Opt a listener in when bots take on its content, with a test. Not included: zone
   enter/exit (`updatePlayerZones`, 113 `onZoneEnter` hooks, driven by `emitPlayerProcess`), for
   the same reason. Tested in `tests/player-process-bots.test.cjs`. The plan was: 58 listeners; most only feed a client (buff, poison and
   freeze timers, world map, equipment stats, voice), which would cost every bot every tick for
   nothing. The gameplay ones (potion and boost timers, teleblock, Agility, random events, the
   F2P members-area check, Barrows, Fight Caves, Warriors' Guild and quest areas) apply once bots
   do that content. Emit it for bots that play as players, and let each gameplay listener opt in
   rather than running all 58.
4. **Trading** with Phase 6.

## Phase 2: account generation by simulation

**State (2026-11-09):**

- [x] stages, mix and archetypes as config (`data/accounts.json`); normal ironmen
- [x] **1** seeded pick of stage, archetype and play time (same seed, same account; tested)
- [ ] **2** simulated play: partly. `Simulator.SppBots.js` applies rates from `training.json`
  (first estimates), but not through a goal planner shared with the live brain (Phase 4 has none yet)
- [ ] **3** unlocks: quests only (by cache requirements, through `complete()`); no diaries,
  combat achievements or collection log
- [x] **4** written through the game's APIs (`Accounts.SppBots.js`: skills, quests, bank, gear)
- [ ] **5** validation pass: not built as a separate check; the gear planner only picks what the
  account may wear (tests cover requirements and quest-locked items)
- [ ] offline progress between sessions: not started (the simulator is ready for it)

A bot's account must look like someone played it. We don't hand out tier templates. We
**simulate a play history**: fast, abstract, offline, with the **same task data the live brain
uses**. A generated account is then exactly what our brain would have produced by playing that
long.

### Stages

| Stage | Roughly | Example |
| --- | --- | --- |
| New | just off Tutorial Island, < 5 h | Level 3, starter items, a few skills in single digits |
| Early | 5 to 100 h | Combat 30-60, F2P quests, first members unlocks, iron/steel/mithril gear |
| Mid | 100 to 600 h | Combat 70-100, rune/dragon gear, Barrows gloves path, first bosses |
| Late | 600 to 2000 h | Combat 100-120, quest cape route, several 90+ skills, raids gear starting |
| Endgame | 2000 h + | Combat 120-126, maxing, top-tier gear, endgame bosses |

The hour ranges and the mix (e.g. 15% new, 30% early, 30% mid, 18% late, 7% endgame) are
config, not code. Archetypes go across stages: main, skiller, pure, PKer. Any of them can
also be a **normal ironman** (no group, ultimate or hardcore). An ironman's simulation never
uses the GE or trades: every item comes from its own gathering, drops, shops or quest rewards,
so its gear and bank follow its skills. The live brain follows the same restriction.

### How the simulation works

1. **Pick** stage, archetype, persona and a target play time from the distributions. Each bot
   has a seed, so the same seed always gives the same account.
2. **Run the planner abstractly.** Start from a fresh account. Repeatedly ask the same goal
   planner and task picker the live brain uses (Phase 4) what to do next. Instead of playing
   the task tick by tick, apply its **rates**: XP/h, GP/h, supplies used, drops, from the task's
   data. Advance the clock. Stop at the target play time.
3. **Apply unlocks as they happen:** quests (only when prerequisites and levels are met),
   achievement diaries, combat achievements, music, collection-log style unlocks.
4. **Write the account** through the game's own APIs, not raw varps: skills, quest stages
   (through the quest plugin's own stage setters), bank, equipment, inventory, attributes,
   play time.
5. **Validate:** every equipped item's requirements are met, every quest's prerequisites are
   done, wealth is believable for the hours played, nothing is impossible. A failed check is a
   bug in the task data or simulator, never something to patch on the account.

### Quests

Two pieces already exist:

- **Quest API:** `QuestRuntime.getRegisteredQuests()` lists every registered quest (195 in
  `plugins/quests/quests/`). `quest.complete(player, { scroll: false, announce: false })`
  completes one as the quest itself does: stage, quest points, the quest's own `onReward`,
  reward item, and the `quest:completed` event other plugins listen to (music, quest cape,
  league tasks, saves). `::quest` (`QuestCommand.plugin.js`) uses the same calls.
- **Requirements:** the cache's quest table (DB table 0, read in
  `plugins/quests/QuestList.QuestRuntime.js`) has, per quest: `requirement_stats` (skill/level
  pairs), `requirement_quests` (row ids), `requirement_questpoints`, `requirement_combat`,
  `requirements_boostable`, `members`, `questpoints`, `stat_xp_awarded` (skill/xp pairs),
  `difficulty`, `length`, `parent_quest` and `has_subquests`.

So the simulator completes a quest only when its cache requirements are met, then calls
`complete()`. If `onReward` gives XP (or a lamp that needs a choice), the simulator checks the
XP actually landed against `stat_xp_awarded`. Quests the cache lists but nobody has registered
are skipped, and so is anything that needs them.

### Offline progress

The same simulator runs **between sessions**. When a bot logs back in, it catches up for the
hours it was "away" (if its persona plays while nobody's watching). Bots keep progressing
without costing tick time, which is how a small online population can sit on a large, living
roster.

### Data

Task rates and requirements live in `plugins/spp-bots/data/` (rule 15): for each task its
requirements, XP/GP per hour by level band, items in and out, unlocks. The wiki is the source
for rates and requirements. The live brain and the simulator read **the same file**: if the
live bot can't actually do a task the way the data says, the data is wrong.

"As many as we can without lag" means a live budget, not a fixed number.

1. **Measure first.** Use `load_spawn` + `perf_sample` ([perf.md](agents/perf.md)) to measure
   the cost of one online bot per activity type, near and far from real players.
2. **Tick budget.** Set a target, e.g. bots may use at most N ms of each 600 ms tick (config).
   The population manager watches tick timings and:
   - logs bots in only while there's headroom
   - logs bots out (at a safe point, like a player ending a session) when the budget is
     exceeded, starting with bots no real player can see
   - never starts a big batch: logins are spread out (upstream already paces 8 per 600 ms)
3. **Level of detail.** Bots near a real player run every tick. Bots nobody can see run less
   often, and bots in an empty region can drop to "offline simulation" (Phase 2) instead of
   ticking at all. Upstream's `lodConfig` is the starting point.
4. **Where they are.** Online bots go where players would be at that time: banks, popular
   training spots, the GE, minigames. Places with real players get more of them.

Layered so each layer can be tested on its own. Reuse upstream's runner and actions at the

```
Persona       who the bot is: likes, play style, risk, chattiness, session habits
  │
Goals         long-term: "99 fishing", "Barrows gloves", "fire cape", "1m gp", "quest cape"
  │
Planner       breaks a goal into tasks with requirements: levels, items, quests, gp
  │
Task picker   utility scoring: goal progress × persona preference × boredom × time left in session
  │
Activity      upstream's Brain frame runner + actions, plus our own activities
  │
Humaniser     reaction delays, idle gaps, breaks, inefficiency, not-quite-optimal choices
```

- **Persona / Goals / Planner / Task picker** are ours, and are shared with the simulator
  (Phase 2).
- **Activity** reuses `Brain.PlayerBots.js` and `brain/actions/` through one adapter file.
  Our activity templates live in our data, registered through a small upstream-able change to
  `ActivityRegistry` (accept templates from another source) or our own registry.
- **Humaniser** wraps action dispatch. AI bots' `pacing` settings
  ([ai-bots.md](ai-bots.md#settings)) are a starting point.
- **LLM** (from AI bots) is optional: it can fill in Persona, Goals and chat, but the brain
  must work without a model.

## Travel (state at the end of 2026-11-09)

Goal: a bot gets from anywhere to anywhere the way a player does: walking, every ladder, door,
shortcut and boat its account allows, and teleports to cut the trip short. Pick up from
[Next steps](#next-steps).

### How a trip works

`createTravelActivity({ api, goal, onDone })` (`Travel.SppBots.js`) is a one-off brain activity
(`brain.replaceRoot`); when it ends the bot goes back to picking its own activities. A trip:

1. **Plans** one search over walking, the transport table (`plugins/agent/data/transports.json`),
   the 601 transports scouts discovered, map doors, teleports, spirit trees and fairy rings, all
   checked against the bot's own account (levels, quests, items it owns anywhere).
2. **Fetches** what the route needs from the nearest bank of any kind: boat fares, tolls, a teleport
   tablet or runes, a house tablet, a fairy ring staff. Then plans again with them on it.
3. **Plays the route** a click at a time, as a client's packets would: walks in 30-tile clicks,
   clicks objects and NPCs through `api.core.ObjectActionPacketListener` / `NPCOptionPacketListener`,
   answers dialogues (`Dialogue.SppBots.js`), casts and breaks teleports, picks menu entries.
4. **Recovers:** a transport that doesn't work is left out and the route planned again (up to 8
   times); a refused teleport is remembered with the server's reason.

### Pieces

- **Planner** (`createTravelSearch`, upstream-able, in `plugins/agent/mcp/TravelRoutes.AgentMcp.js`):
  A* that runs a slice at a time. spp-bots runs it from the plugin's tick task: 30 ms a tick in
  all while the server's slowest recent tick is under 100 ms, else 12; 500-expansion chunks;
  searches under 20k expansions first, least advanced first, then the oldest; searches under 60k
  always run, at most 8 bigger ones; 250k cap ("too far", remembered 10 minutes by region pair for
  every bot); heuristic weight 2 (routes a little longer than the shortest, found far faster). A
  route that avoids the Wilderness is tried first when neither end is in it (the Wilderness level
  is cached per tile). With `isGoal` and no goal tile it's Dijkstra for the nearest matching tile
  (a bank, a gathering spot), capped at 60k.
- **Teleports** (`Teleports.SppBots.js`), from the server's own tables so a bot lands where the
  server puts it: spellbook teleports, tablets and scrolls, charged jewellery, minigame teleports
  (Castle Wars, Clan Wars/Ferox and the others that need nothing the server can't check). From the
  bot's tile: what it carries, and the minigame teleport off cooldown. From every bank stand: what
  it owns in the bank. Cost = cast ticks + a use cost (spell 10, tablet/jewellery 25, house 20,
  minigame 60) + 10 for a bank visit, so nobody spends a charge to save a few steps. Cast like a
  client: the spell's button (`emitInterfaceActionClick`, so quest locks apply), a tablet's Break or
  a piece's destination (`ItemActionPacketListener.handleAction`), the grouping tab's teleport
  button. `teleport:can-start` is asked for each destination while planning; the bot stands still
  before casting (the minigame teleport won't start while walking).
- **The house** (`houseHops` / `houseRide`): in with a house tablet ("Inside") or Teleport to House,
  out through the portal nexus (each of its slots) or the jewellery box (each slot its tier has).
  Inside, the bot opens the built piece's Teleport Menu and sends the slot as the menu's
  pause-button click until it's carried out; if anything fails inside it leaves through its exit
  portal. Bots with 72+ Construction on members worlds get a house once (Construction's
  `::maxhouse` layout, roster flag `house`). Construction's modules are required lazily from
  `Imports.SppBots.js`: requiring them at load broke both plugins.
- **Spirit trees and fairy rings** (`Networks.SppBots.js`): transports from each tree or ring to
  every destination the server lists for the player. Spirit trees: Travel, then the menu slot
  (187:3). Fairy rings: Fairytale II access and a Dramen/Lunar staff (fetched from the bank like a
  fare), wielded at the ring; Configure, the dials (398:19/21/23) to the code, confirm (398:26).
- **Banks of every kind** (`Banks.SppBots.js`, `createBankVisit`): booths and chests (any loc named
  like a bank with a Bank/Use option; upstream's `BANK_BOOTH_IDS` also names decorative booths)
  and bankers (used across the booth in front of them: Bank doesn't work from behind, though the
  floor there is often walkable). The visit searches outward for the nearest stand of a bank the
  bot can walk to (no teleports, nothing to fetch), so a guild it isn't in doesn't count; with
  none in walking distance it makes one trip with teleports to the nearest bank as the crow
  flies. It clicks like a client (a counter's banker is the one in front of the bot) and takes the
  bot's BANKING status as open (`openBank` gives bots no interface). A stand the server's reach
  check or "I can't reach that!" rules out is avoided by every bot; a bank that didn't open, by
  that bot for its session. Activities and the traveller both use it; upstream's booth-only bank
  action isn't used any more. Chest positions come from the object index, which tracks them now.
- **Fares and tolls:** items a route's transports need (the table's `items`, and `Pay-toll(Ngp)`
  on an object such as the Al Kharid gate, paid with the bot's own coins) are fetched first; a
  part-stack is topped up, a full inventory banked.
- **Refusals:** a bot's game messages are kept from its first cast. A teleport that doesn't
  happen is put down to them: a lasting reason (a quest, a level, no house) keeps the bot off it
  for the session; anything else (a cooldown, busy, no message) for 5 minutes.
- **Travel kits** (`gear.json` `travel`): runes, tablets, jewellery, a Dramen staff (Lost City),
  house tablets, by level, members and wealth (ironmen by the levels to make them). `kit` versions
  them: bots generated earlier get the newer entries once at login (`grantTravelKit`, roster
  `travelKit`, now 3).
- **Small things that mattered:** NPCs are matched with `getCurrentDefinition(player)` (multi-NPCs
  such as Captain Tobias); object lookups load the region's map files first (a bot alone in a
  region found no tree or gate); toll gates are matched by name (the map holds a multi-loc's raw
  id); an open interface is closed before a click (a click while busy is dropped); an already
  opened map door is walked through; charter ships, canoes and "Shantay Pass arrest" are left out;
  bots never save or log in at instance coordinates (x >= 6400).
- **Reach and scouting:** `::sppbots reach` floods the world graph (forwards and backwards, ~50 s,
  no lag) and writes `data/saves/spp-bots/reach-report.json` with cut-off pieces and their cause;
  `::sppbots probe x y z` explains a tile. Scouting is finished (`discovered-transports.json`).
  Bank stands are filtered to tiles the last reach run reached, so run `reach` after a restart.

### Testing on the live server

The spp-bots server runs from this checkout under nodemon (`scripts/spp/server.sh`, game 43720,
agent MCP 49820), so editing a plugin file restarts it: bots log out, trips and tours stop, and
the reach run is lost. After a restart: `::sppbots reach`, then test. Markdown edits don't restart.

- `::sppbots travel <name> x y [z]`: one bot; the result is in chat and the log as
  `[spp-bots] travel: ...`.
- `::sppbots trip <name>`: where a bot's trip is (planning and how far, which leg, the ride, the
  bank visit) and its brain's frames (activity, state, fail reason, rest), in chat and the log as
  `[spp-bots] trip`.
- `::sppbots planner`: the planner's queue (count in chat, every search in the log as
  `[spp-bots] planner`, with who, from, goal, expansions, age).
- `::sppbots tour <n> [banks] | status | stop`: n bots to random reachable NPCs (or bank stands) and
  back; `data/saves/spp-bots/tour-report.json` has every leg and a summary.
- Always logged: `spp_bots_transport_failed`, `spp_bots_no_route`, `spp_bots_travel_fetch`,
  `spp_bots_teleport`, `spp_bots_teleport_refused`, `spp_bots_network`, `spp_bots_bank_failed`, `spp_bots_bank_bad_stand`
  (with where the bot stood and what it clicked), `spp_bots_house`, `spp_bots_slow_plan`.
- Agent testing used account `sppdev` (`::master` levels; it now has a max house from
  `::maxhouse`, `::restorehouse` undoes it). The roster's `house: true` bots own houses.

### Measured

Same machine as another running tsps server; 1 real player; `perf_sample` over 30 s.

| Bots online | Avg tick | Max tick | spp-bots' own loop |
| --- | --- | --- | --- |
| 10 | 8.6 ms | 19 ms | under 1 ms |
| 50 | 19.7 ms | 68 ms | |
| 150 | 35.3 ms | 72 ms | 4.9 ms |
| 300 | 45.9 ms | 83 ms | 4.7 ms |

2026-11-09, 200 bots with banking, site trips and the route planner at its 30 ms budget: 39 ms
average, 84 ms max (40-52 ms average while a 25-bot tour ran too).

Cost grows more slowly than the bot count, because bots no real player can see think every 4th
tick. At 300 the server used about 1.6 GB. The default is **200 online, 400 in the roster**:
about 40 ms of a 600 ms tick, leaving headroom for real players (bots near them think every
tick) and busy areas. Raise it with `::sppbots online <n>` or `"SppBots:population"`.
